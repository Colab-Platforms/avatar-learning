# API_DOCUMENTATION.md

REST API, all under **`/api`** (mounted in [backend/src/routes.ts](backend/src/routes.ts)). Verified from route files **[code]**; nothing was called at runtime. For per-endpoint body fields, open the module's `*.validators.ts` (Joi) — only auth bodies are summarised here.

## Conventions
- **Response envelope:** `{ "status": boolean, "data": any, "message": string }` via `sendResponse` ([responseUtils.ts](backend/src/utils/responseUtils.ts)).
- **Errors:** thrown `ApiError(message, code)` → [errorHandler.ts](backend/src/middlewares/errorHandler.ts) → `{status:false, data:<error object>, message, }` with `err.statusCode` (default 500). Unknown routes → `notFoundHandler`. Rate limit → 429 with envelope. CORS rejection → generic error (500) logged as "Origin not allowed by CORS".
- **Status codes used:** 200, 201, 202, 204, 400, 401, 403, 404, 405, 409, 422, 429, 500 ([statusCodes.ts](backend/src/utils/statusCodes.ts)). 401 = missing/invalid/expired token; 403 = role insufficient or profile incomplete ("Please complete your profile…") or inactive account.
- **Auth:** `Authorization: Bearer <accessToken>`. Legend below: **Pub** public · **U** `auth("USER")` (+ `requireCompleteProfile` = **U+P**) · **A** `auth("ADMIN")` (ADMIN or SUPERADMIN) · **SA** SUPERADMIN. Higher roles pass lower checks.
- `express.json` keeps `req.rawBody` for webhook signatures; all input passes xss sanitize middleware.
- Param name quirks: course routes accept `:courseId` as id; D2H gates resolve a course from `courseId` in query/body/params (id or slug).

## Business Admin — `/api/business-admin` (Avatar Adaption; separate from `/api/admin`)
Auth: `auth("ADMIN")` **plus** `requireBusinessAdmin`: SUPERADMIN always; ADMIN only if their email is in env `BUSINESS_ADMIN_EMAILS` (comma-separated, case-insensitive); USER never → 403. Unset allowlist = only SUPERADMIN. All read-only. Code: `backend/src/modules/business-admin/`.
`GET /me` → `{role, access, userId}` · `GET /overview` (counts + booleans-only integration status incl. `outboundSending: "inactive"|"ready"`) · `GET /whatsapp/team` (people who can open Business Admin).
**Inbox (all behind the same two middlewares, writes included):** `GET /whatsapp/conversations?filter=all|unread|mine|unassigned&assignee&q&page&pageSize<=50` (newest activity first; name/phone search; `unreadTotal`) · `GET /whatsapp/conversations/:waId` (contact + 24h window state) · `GET .../messages?limit<=100&before=<cursor>` (oldest to newest page; cursor over createdAt,id) · `POST .../messages {text<=4096, clientRequestId}` -> 201 new / 200 repeat, **idempotent per clientRequestId**; 409 `WINDOW_CLOSED` (the customer's last message is over 24h old: WhatsApp requires an approved template, and templates are NOT implemented), 503 `NOT_CONFIGURED` (needs WHATSAPP_ENABLED + access token + phone number id + **WHATSAPP_OUTBOUND_ENABLED=true**), 404 `NO_CONVERSATION`; a WhatsApp rejection is a 201 with the stored message in `failed` state and a readable reason (timeouts are flagged `ambiguous`) · `POST /whatsapp/messages/:id/retry` (failed messages only; creates a new row under key `retry-of:<id>`, so a double click sends once) · `POST .../read {upTo?}` (team-wide read marker, never moves back) · `PUT .../assignment {assigneeId|null}` (422 unless the target is a team member; history recorded) · `GET .../events` · `POST .../notes {body<=2000}` (internal only, never sent). Message and note text is read from the raw JSON body so the global HTML sanitizer cannot alter what is sent. Message states: sending, sent, delivered, read, failed, unconfirmed (SENDING for over 2 minutes). Status webhooks update the same rows through the existing monotonic state machine. Send limiter: 60/min per client IP.

**Message `state` (outbound)** — real WhatsApp: `sending` → `accepted` (Graph API returned a message id; `sentAt` still empty) → `sent` (Meta status webhook filled `sentAt`) → `delivered` → `read`, or `failed`/`unconfirmed`. `simulated` is the dev sandbox only (mock sender; nothing reached WhatsApp) and is never produced for a real send; a message whose id starts `wamid.DEVTEST` is always `simulated`. Each message also carries `simulated: boolean` and `timeline {acceptedAt,sentAt,deliveredAt,readAt,failedAt}`. `acceptedAt` is stored in the message payload; no schema change. Code: `inbox.plan.ts` (`messageState`), `inbox.store.ts` (`markSent`, `sandbox` option).
**Permissions + Admin Management (migration `20261119190000_add_business_admin_access`, NOT applied):** access is now resolved from the database on every request: SUPERADMIN = everything incl. `admins`; ADMIN = the modules in `business_admin_access` (dashboard, inbox, leads, customers, agents, automations, integrations, analytics, team, settings), else legacy `BUSINESS_ADMIN_EMAILS` = all modules except `admins`; inactive/deleted accounts are refused immediately. Each endpoint group needs its module (`/overview`: dashboard|integrations|analytics|inbox; `/whatsapp/*`: inbox; `/admins*`: Super Admin only). `/me` now returns `{role, access, userId, modules, isSuperAdmin}`. **Super Admin only:** `GET /admins/meta` (modules + role presets MANAGER, SUPPORT_AGENT, ANALYST, CUSTOM) · `GET /admins?q&page&pageSize<=100` · `POST /admins {name,email,password,roleKey,modules?}` (creates a verified local ADMIN user; 409 if the email exists on ANY account; password >=10 chars, 3 of 4 character classes, no common words/name/email; bcrypt cost 12; **Super Admins cannot be created** through the API) · `PATCH /admins/:id {name?,roleKey?,modules?,isActive?}` (Super Admins are protected; you cannot deactivate yourself; deactivating also deletes the person's refresh sessions) · `POST /admins/:id/reset-password {password}` (deletes their sessions). Passwords are read from the raw JSON body so the HTML sanitizer cannot alter them; never logged or returned.

**Inbox extras (Stage A, behind the `inbox` module; every route needs the same login + Business Admin checks) [code, mock-tested only; no real Meta call made]:** `GET /whatsapp/search?q&waId` (message text search) · `GET /whatsapp/templates[?refresh=1]` (live from Meta `GET /{WABA_ID}/message_templates`; needs `WHATSAPP_BUSINESS_ACCOUNT_ID`; only approved, non-authentication, body-variable-only, no-media-header templates are `sendable`, others carry `unsupportedReason`) · `POST /whatsapp/conversations/:waId/templates {name, language, variables[], clientRequestId}` (outside the 24h window requires the contact's opt-in to be GRANTED with recorded evidence; WITHDRAWN blocks every send) · `POST /whatsapp/conversations/:waId/media` (multipart `file`, optional `caption`, `clientRequestId`, `replyToMessageId`; image/video/audio/document; Meta size limits enforced; uploaded to Meta then sent by media id) · `GET /whatsapp/messages/:messageId/media` (authenticated streaming proxy; the Meta token never reaches the browser) · `GET /whatsapp/conversations/:waId/profile` and `GET /whatsapp/tags` · `GET /whatsapp/groups/status` (honest status: group messaging is NOT implemented and Meta Groups API eligibility is NOT verified) · `GET/POST /whatsapp/contacts`, `POST /whatsapp/contacts/import` (never changes consent), `GET/PATCH/DELETE /whatsapp/contacts/:id` (deletes the local record only), `PUT /whatsapp/contacts/:id/opt-in {status, evidence, note}` (GRANTED needs an evidence type and reference). Also `GET .../messages?until=` and `replyToMessageId` on send. An inbound exact STOP/UNSUBSCRIBE withdraws consent immediately (webhook hook).

**Website analytics (Stage B, `analytics` module) [code, mock-tested only; no real Clarity call made]:** source is the Microsoft Clarity Data Export API (`CLARITY_API_TOKEN`; `CLARITY_PROJECT_ID` only builds dashboard links). `GET /analytics/status` (booleans, requests used today of 8, dashboard links, and an `unavailable` list: live visitors, new vs returning, entry/exit, journeys, recordings, heatmaps, ranges over 3 days, arbitrary-period comparison) · `GET /analytics/overview?days=1|2|3[&refresh=1]` → `{totals, meta{fetchedAt, source: cache|clarity, stale}}` · `GET /analytics/breakdown?dimension=Browser|Device|Country/Region|OS|Source|Medium|Campaign|Channel|URL&days=1|2|3` → `{rows, pages, total, meta}` · `GET /analytics/history` (stored snapshots, the only history beyond Clarity's 3 days). Results are stored in `clarity_snapshots` and reused for 6 hours; the server spends at most 8 Clarity requests per UTC day (Clarity allows about 10) and falls back to the last stored data (`stale: true`) when Clarity cannot be asked. Errors carry `data.code`: `NOT_CONFIGURED` (503), `INVALID_TOKEN` (409), `DAILY_LIMIT` (429), `UPSTREAM` (503). Response field names from Clarity are parsed tolerantly and are UNVERIFIED against a live project.

### Business Admin — Template Manager & Automations (module `automations`; routes exist only when wired in `business-admin.route.ts`)
All under `/api/business-admin`, same auth as above. Writes are rate-limited (30/min/IP). [code] Mocked-network tests only; no real Meta call has been made.
- `GET /automations/meta` → `{ events[], enabled, counts }` (event catalog from `automation.events.ts`; `enabled` = `WHATSAPP_AUTOMATION_ENABLED`).
- `GET /automations/templates` → sendable (APPROVED) templates with `variables[]` (live from Meta, cached ≤5 min).
- `GET|POST /automations/rules`, `PUT /automations/rules/:id`, `PUT /automations/rules/:id/active` `{active}`, `DELETE /automations/rules/:id`. Rules are created **inactive**; a rule can only reference an approved, sendable template and must map every variable (`{source:"field",key,fallback?}` or `{source:"static",value}`).
- `GET /automations/executions?status=&ruleId=&page=` (history, refreshes delivery receipts first), `POST /automations/executions/:id/retry` (refused for unconfirmed sends).
- `GET|POST /template-manager/templates`, `GET|PUT|DELETE /template-manager/templates/:id`, `POST /template-manager/templates/:id/submit`, `POST /template-manager/sync`, `POST /template-manager/example` (multipart sample media → Meta resumable upload; needs `WHATSAPP_APP_ID`). Create/update save a local **DRAFT** (never implies approval); submit/edit call Meta and store **only Meta's reported status**; sync pages through all Meta templates. Only unsubmitted drafts can be deleted. Error body `data.errors[] = {field,message}` for validation failures.
- Activities: `GET /automations/meta` now returns the nine activities (`demo.requested`, `user.registered`, `demo.scheduled`, `demo.rescheduled`, `demo.cancelled`, `contact.submitted`, `webinar.registered`, `payment.succeeded`, `course.enrolled`) each with its real endpoint (`automation.endpoints.ts`) and suggested template wording; `POST /automations/suggested-templates` saves LOCAL template drafts from that wording (nothing goes to Meta). `/template-manager/*` is allowed for modules `automations` OR `inbox` (the manager lives in Inbox → Templates).
- Website hooks (call `emitAutomationEvent`, `automation.emit.ts`; no-op unless `WHATSAPP_AUTOMATION_ENABLED=true`; fire-and-forget; only after success): `POST /api/auth/verify-otp` (user.registered), `POST /api/webinar/verify-payment` + free registration + Razorpay webhook (webinar.registered, in `finalizeAsPaid`), `POST /api/payment/verify` + both payment webhooks (payment.succeeded, and course.enrolled for a newly granted course, in `completePayment`), `POST /api/courses/:courseId/enroll` (course.enrolled). NOT connected: demo.* (no demo endpoint exists) and contact.submitted (`POST /api/contact` collects no phone number).
- Dev sandbox only: `POST /automations/simulate` `{event, phone, eventId?}` exists only when the dev sandbox supplies a simulator (never in production); `GET /automations/meta` then returns `sandbox: true`. The payment hook's event id is the gateway ORDER id, so verify + Razorpay + Cashfree for one order dedupe.
- Reusable trigger (internal): `automation.trigger({event, eventId, phone, fields})` from `business-admin.route.ts`; queues one execution per active rule (idempotent on rule+eventId). Worker `src/jobs/automation.job.ts` runs only if `WHATSAPP_AUTOMATION_ENABLED=true` at boot.
